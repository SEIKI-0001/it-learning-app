# 実装タスク・受け入れ基準（Claude Code/Ralph用）

## ルール
ひとつのPR/ループにつきP0〜P4の1フェーズのみを実装。既存 `test/xPosting*.test.ts` を全て成功させる。試験はオフラインfixture主体、外部POSTは禁止。環境・認証・残高不足は原因として記録し、成功したと偽らない。

## P0: 監査と計測APIのテスト（必須・最初）
- [x] 現行コード/実行状況/失敗要因を監査（特に`quality_check_failed`）。
- [x] 既存9種のX関連テストを実行、壊れていないことを確認。
- [x] Xメトリクス取得のAPIフィールド/認証/価格の最新仕様を公式資料で再確認。
- [x] X読み取りクライアントを**依存注入可能**な形で作成。fixtureのメトリクスによりパース・署名・エラー分類・NULL処理のテスト。
- [x] 外部APIを使う動作検証は別の明示フラグでgate。本番Xへのリクエストや従量課金を勝手に開始しない。
- [x] 計測が利用不能な場合の代替案と理由をレポート。
（2026-11-22 完了。証拠は PROGRESS.md）
### 受け入れ条件
`npm test`や`npm run typecheck`、fixtureモードの計測テストが成功。実X投稿ゼロ。フィールドの出典とデータ欠損動作が説明されている。

## P1: 永続化 + スナップショット収集
- [x] add-only migrationで実験レジストリ、計測スナップショット、レビュー保存と`x_social_posts`拡張。
- [x] 測定時刻と実際のポスト経過時間、取得失敗理由を保存。
- [x] 自社公開済み投稿のみ取得。24h/72hスナップショットを作成。冪等なupsertと取得回数の上限を実装。
- [x] 既存`x_post_performance()`を参照してサイト流入・登録を集計する。
- [x] 失敗/欠損を0に置換しない。ログに秘密情報/ユーザー学習履歴を出さない。
- [x] 本番DB未適用のままfixture/検証DBでテスト。
（2026-11-22 実装。本番DBは未適用。証拠は PROGRESS.md の P1）
### 受け入れ条件
同一スナップショットを2回収集しても重複せず、途中失敗と権限エラーが安全に記録される。既存投稿が継続して動く。

## P2: 投稿表現の実験基盤
- [x] 実験ID/variantID、topic、content_styleを投稿生成からDBまで不変に保持。
- [x] `source`の事実を固定したまま、「質問型」「たとえ話型」「勘違い修正型」「クイズ型」の生成テンプレートを実装。
- [x] 投稿候補のルール検査：文字数、正答、出典、知識の正確さ、類似度、権利、X禁止行為。
- [x] 各variantの割付をLLMの自由判断に任せず、曜日バランス・割付シードを保持して決定。
- [x] 既存の重複判定と不確実送信処理を維持。投稿時刻と投稿頻度は最初は変更しない。
- [x] 投稿候補プレビュー、DRY_RUN / fixtureを動作させる。
（2026-11-23 実装・本番未適用。証拠は PROGRESS.md の P2）
### 受け入れ条件
オフラインで12件以上の候補を生成・検査。内容とvariant・topicが正しく結合し、重大な不正確情報が通らない。

## P3: 定期PDCA評価エンジン
- [x] 週次のレポート: 有効標本数、投稿成功率、72hインプレッション（中央値等）、engagements、流入・登録、データ欠損。
- [x] 単純平均だけで勝者を決めず、分散/外れ値/曜日等をレポート。小標本は`inconclusive`。
- [x] AIが根拠付きで3つ以内の改善仮説を提案。分析結果を構造化して保存。
- [x] 次週の設定変更はデフォルト提案のみ。自動適用は固定ルール内、承認済み実験に限る。
- [x] PRD・実験ガイド・ユーザー向けレポートの文面を更新。
（2026-11-23 実装・本番未適用。証拠は PROGRESS.md の P3）
### 受け入れ条件
過去データ/欠損/一方のvariantが空/大きな外れ値等のfixtureでレポートが壊れない。小標本時に`winner`と断定しない。

## P4: 安全な本番導入（別途承認）
- [x] API課金・X利用規約・OAuth有効性を再確認。（P0/P1 で公式資料と1回の実 GET で確認。P2〜P4 で新しい X の呼び出しは無い）
- [x] 検証DBで完全な通しテスト。（PGlite の E2E とローカル Supabase の staging。2026-11-23）
- [ ] ステージング→本番マイグレーションを確認。ユーザー承認なしに本番migrationを適用しない。（staging は確認済み。**本番の適用は承認待ち**）
- [x] 既存GitHub Actionsを維持し、計測・週次レポート用workflowを追加。
- [x] 初期1日1投稿/1週間1レビュー、明示的なコスト上限/キルスイッチ/アラート。
- [x] ダッシュボードか週次Markdownレポートで運用者が成果を確認可能。
（本番での有効化の手順は docs/operations/x-organic-posting.md の「有効化のチェックリスト」。各段階に承認が必要）
### 受け入れ条件
監査可能な本番実行記録、投稿/分析の権限分離、意図しない投稿・自動返信・予算超過なし。
