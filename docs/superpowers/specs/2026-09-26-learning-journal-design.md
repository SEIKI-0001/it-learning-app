# 学習の記録：実装設計案

状態: ユーザー承認済み。2026-09-26の5点の修正を反映。
基準: origin/main 0c6d822。ユーザー提供の実装指示と添付画像を優先する。

## 目的と完成像

日次・週次・CHECKPOINT突破を、一人の学習史として保存する。過去の自分の成長を具体的な根拠とともに振り返れることを目的とする。手入力、対話、ランキング、SNS共有、目標入力は追加しない。

添付画像の生成りの紙、濃紺、控えめな金色、細い装飾、縦一本のタイムライン、余白を再現する。スマートフォンの外枠やOSのステータスバーはアプリには描画しない。もちっとの大量配置やゲーム的な演出は行わない。

## 現状調査

- `app/report/page.tsx` はブラウザーの AppState から閲覧時にレポートを生成する。期間は月〜日ではなく、今日を含む直近7暦日。
- `lib/weeklyReportFacts.ts` は回答数・正答率・学習日数・前期比・初見と解き直し・以前の誤答の克服・理解度変化・苦手・再開・分野別回答数・復習待ち・CP条件・累計・次の学習候補を計算する。
- `components/report/WeeklyReportView.tsx` は総括、成長、数値、気づき、課題、次の行動、モチットの文章を表示する。一部の詳細な事実は画面に直接列挙されない。
- `lib/useWeeklyNarrative.ts` はAI文章をlocalStorageに1件だけ保存する。入力が変わると文章も変わる。
- `app/api/weekly-report/route.ts` は渡された事実を検査してGeminiで文章化する。レポートのDB保存はない。
- `daily_progress_reports` は手動の達成度報告。今回の自動日次記録の保存先には転用しない。
- `question_attempts.time_spent_seconds` はnullable。旧`user_answers`には時間列がない。回答時刻の間隔から実測学習時間を捏造しない。
- CP突破試験の結果は`user_progress.checkpoint_progress.finalExamAttempts`にあるが、突破時点の累計・文章のsnapshotはない。
- 内部ユーザーIDは`line_users.id`。Google認証IDと同一ではない。`getInternalUserId`で解決する。
- アカウント統合の処理があるため、新しい保存表も統合対象に加える必要がある。

## 採用する構成

既存の分析・詳細コンポーネントを再利用し、統一した保存表と生成サービスを追加する。日次・週次・CPごとに別々の保存表を増やす案は、期間検索・既読管理・統合処理が分散するため採用しない。現在のlocalStorageキャッシュだけを延長する案では、端末間の永続性を満たせない。

- `/journal`: 月選択、4種のフィルター、時系列カード。
- `/journal/[recordId]`: 保存済みの詳細。週次は既存の分析項目をすべて維持し、学習時間、分野、進捗、CPとの距離も明示する。
- `/report`: 既存URLとして保持し、週次の記録への入口に接続する。リンク切れを作らない。
- 既存の「進捗」ナビ・Progressページは維持する。Progressの「くわしく見る」と「その他」に学習の記録を追加し、週間レポートからもリンクする。Progressは現在地、学習の記録は過去の歩みを担う。
- `WeeklyReportView`は保存されたfactsとnarrativeを受け取れるよう分離し、過去の詳細を開いた時にAIを再実行しない。

## 日付と確定

週間レポートは現行の「対象日を含む直近7暦日（ローカル時刻）」を維持する。クライアントのIANAタイムゾーンを検証して生成に用い、期間とタイムゾーンを保存する。月曜〜日曜への変更は行わない。定期処理は保存済みタイムゾーンを用いる。

日次は意味のある学習活動（回答、完了済みの実学習）がある日のみ生成する。0回答・0学習の空の日次は作らない。当日分は集計中として保存・更新し、翌日以降にfactsを確定する。週次は対象日を含む直近7日のfactsを生成時に確定保存する。初回生成後は7日ごとに生成するが、期間算出式は変えない。非活動期間は次回の日次・週次の再開分析に用いる。

定期実行で確定処理を行い、ログイン時にも未処理期間を補完する。再実行・複数端末・同時リクエストでも重複しない。長い未処理期間はページ分割したジョブで進める。factsの確定とAI文章の確定を分離する。AI失敗時はtemplateを表示し、同一の保存済みfactsだけで非同期再試行する。AI版の検証成功後は文章も固定する。試行回数、次回試行日時、処理leaseを持たせ、並行処理と連続失敗を制御する。

週次の月所属は期間終了日で決める。並び順は対象日時の降順で固定し、未読だから過去のカードを時系列から移動させない。他の月に未読があれば、その月・レポートへの小さな案内をヘッダーに出す。

## 保存構造

`learning_journal_records`を追加する。

- `id`, `user_id`, `record_type`（daily / weekly / checkpoint）
- `period_start`, `period_end`, `occurred_at`, `timezone`
- `record_key`（日付、週の開始日、CP初回突破の識別子）
- `schema_version`, `snapshot`（指標・詳細facts・根拠・データ充足度）
- `narrative`（ai/templateの区別）、`narrative_status`, `narrative_attempts`, `next_retry_at`, `lease_until`
- `comparison`（比較期間、対象指標、前後の値、件数）
- `checkpoint`（CP識別子・名称・突破時点の情報・次のCP案内）
- `created_at`, `finalized_at`, `first_viewed_at`

通常生成では`(user_id, record_type, record_key)`の一意制約で重複を防ぐ。DB側でも確定後のfacts変更とAI成功後の本文変更を拒否する。templateから検証済みAIへの一度の更新と既読更新を認める。期間検索に`(user_id, period_end, record_type)`の索引を付ける。

個人データの表としてRLSを有効化し、匿名・ブラウザーからの直接書き込みは許可しない。認証済みのサーバーAPIが内部IDで所有者を確認する。クライアントが送るuserIdや集計結果を保存の権威にしない。

アカウント統合では両方の確定snapshotを保持する。内容が異なる同一期間の記録を再集計・上書きしないよう、元アカウントを含む移行キーで衝突を解決する。アカウント削除時は既存の削除規約に従う。

## 生成と移行

サーバーで保存済みの回答・進捗を読み、日次・週次の事実を作る。`user_answers`と`question_attempts`の同じ回答を二重計上しない。既存の照合規則と回答の識別子・時刻・問題IDを確認し、対応するテストを追加する。過去問を含めて集計対象と欠測範囲を明確にする。

学習時間には実測の回答時間を利用し、未計測がある場合は「記録された時間」または「一部未計測」と示す。全件未計測なら「未計測」。今後の未計測の学習経路は既存の回答保存経路に計測値を追加する。放置時間を学習時間として無制限に加算しない。

CPの初回突破では、突破記録とsnapshotを同じDBトランザクションで保存する。AIの外部呼び出しはトランザクションに入れず、まず事実を耐久保存してジョブで文章を確定する。ジョブ失敗は再試行可能にし、学習の保存自体をAI障害で失敗させない。既存の合格判定やCP進行条件を変更しない。

旧データは取得できる履歴だけから一度だけ移行する。旧CPは実際の突破日時が分かるものだけを記録する。当時の完了セクション数など復元できない項目は不明として保持し、現在値を代入しない。日時のない移行推定CPも過去の実績として作らない。旧週次レポートにはサーバーアーカイブが存在しないため、当時のAI文章が残っていると装わない。

## 文章の方針

優先順位は、誤答からの回復、苦手の改善、定着、継続、再開、新分野、学習量。実データの根拠IDと比較値を添えてAIに渡す。分野別比較を表示する時は同じ分野・同じ指標の前後値と件数を使う。

データが少なければ参考値であることを明記し、一回の正解を「安定して定着した」と断定しない。課題は結果、データで言える要因、実行可能な改善の順に述べる。観測できない原因を性格や努力不足に結び付けない。AIの数値検証・禁止表現検証を維持する。テンプレートにも同じルールを適用する。

## UIと既読

日次は紺、週次は茶金、CPは少し大きな金色マーカー。カードは白〜生成り、細い金の罫線、見出しは落ち着いた明朝系とし、本文は小画面でも読める大きさを確保する。

週次カードは4つの指標、短い文章、必要な比較に留める。右矢印と「レポートを見る」を表示し、hover・押下・キーボードfocusの反応を用意する。未読は小さなNEW、少し強い金の枠、淡い明るさに加え、「今週の振り返りが届いています」「レポートを見る →」を表示する。通常の週次より閲覧を促し、時系列順は変更しない。

詳細の取得に成功して画面が表示された後、専用の既読APIを呼ぶ。リンクのプリフェッチ・一覧取得では既読にしない。`first_viewed_at IS NULL`の場合だけDB時刻を保存し、以後の閲覧で初回時刻を変えない。

CP演出は新しい突破記録に約1秒だけ。過去月への移動で毎回再生しない。`prefers-reduced-motion`では省略する。空の月、フィルター0件、読み込み、保存未完了、取得失敗をそれぞれ区別する。

## 検証とリリース

- 日付境界、月跨ぎ、直近7暦日の週、0件、部分的な時間欠測、回答重複を検証する。
- 確定後の不変性、同時生成、ジョブ再試行、CP初回突破の原子性をDBテストで検証する。
- 所有者以外のアクセス拒否、既読の初回時刻、アカウント統合時の履歴保持を検証する。
- 旧レポートの全分析項目が詳細に残り、保存済み詳細の閲覧でAI生成をしないことを検証する。
- スマートフォン幅とデスクトップで添付画像との比較、長い日本語、4フィルター、月切替、未読、motion設定をブラウザーで確認する。
- `npm run typecheck`、`npm run lint`、`npm test`を実行する。問題データは変更しない。
- DB migrationと既存環境の生成ジョブを確認し、origin/mainの最新変更を取り込んでからmainへマージ・pushする。本番はmainからのみ反映する。
